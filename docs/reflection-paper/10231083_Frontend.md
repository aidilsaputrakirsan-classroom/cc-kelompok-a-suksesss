# Reflection Paper – Frontend

## 1. Pendahuluan
Mengerjakan proyek SafeSpace memberikan pengalaman yang sangat berbeda bagi saya. Sebagai Lead Frontend, tugas saya di sini bukan sekadar membuat tampilan antarmuka yang bagus, tetapi memastikan semua komponen tersebut dapat terhubung dengan mulus ke ekosistem microservices backend yang cukup rumit. Dari proses ini, saya menyadari bahwa frontend berfungsi layaknya jembatan utama bagi pengguna. Refleksi ini akan membahas bagaimana saya mengambil keputusan teknis, menghadapi tantangan integrasi, serta pelajaran berharga yang saya dapatkan selama berkolaborasi dalam tim.

## 2. Kontribusi Teknis
Fokus utama saya dimulai dari penyusunan halaman Login dan Register. Untuk implementasi autentikasi JWT, saya mengambil keputusan untuk menyimpan token di `sessionStorage` alih-alih `localStorage`. Pertimbangan saya cukup sederhana namun krusial: `sessionStorage` lebih aman karena token akan otomatis terhapus saat browser ditutup, sehingga mengurangi risiko jika perangkat digunakan oleh orang lain. Setelah autentikasi berjalan, saya melanjutkan pengembangan Dashboard BK dengan menambahkan fitur pencarian dan pengurutan data agar lebih mudah digunakan oleh guru. Selain itu, kontribusi yang cukup menantang bagi saya adalah merancang halaman *health check dashboard*. Di sini, frontend bertugas mengambil data dari API Gateway untuk memberikan gambaran kondisi sistem secara real-time kepada seluruh tim.

## 3. Keputusan Arsitektur & Teknis
Setiap pilihan teknologi yang saya ambil memiliki alasan yang mendasari, bukan sekadar mengikuti tren. Saya memilih kombinasi React dan Vite karena pengalaman pengembangannya jauh lebih efisien. Vite menawarkan kecepatan *build* yang sangat cepat dan ringan dibandingkan Create React App, yang sangat membantu menjaga produktivitas tim. Untuk mengatur alur data di dalam aplikasi, saya memutuskan untuk menggunakan React Context API bersama *hooks*. Mengingat skala proyek ini, menurut saya pendekatan tersebut sudah cukup efektif untuk menghindari *prop drilling* tanpa perlu menambah kerumitan kode dengan *state management library* yang lebih berat seperti Redux.

## 4. Tantangan & Solusi
Tentu saja, proses pengembangan tidak selalu berjalan mulus. Hambatan pertama yang saya hadapi adalah error CORS. Saat frontend di `localhost:5173` mencoba mengakses backend, browser menolak permintaan tersebut. Masalah ini memaksa saya untuk lebih memahami batasan keamanan bawaan browser, dan saya harus berdiskusi langsung dengan tim backend agar mereka menambahkan konfigurasi *origin* yang tepat melalui *environment variable*.

Tantangan yang cukup unik muncul saat saya mengerjakan *health check dashboard*. Awalnya, kartu status di antarmuka terus menampilkan tulisan "UNREACHABLE" atau memunculkan error `ERR_EMPTY_RESPONSE`. Setelah saya telusuri, saya menyadari bahwa ini bukan karena ada *bug* pada kode saya, melainkan karena pada tahap tersebut frontend memang belum memiliki metrik yang siap untuk memanggil API *health* dari backend. Daripada membiarkan kartunya kosong dan membingungkan, saya mengambil keputusan desain untuk sengaja menampilkan status "UNREACHABLE" tersebut sebagai *placeholder* sementara. Dari kejadian ini, saya belajar tentang konsep *graceful degradation*, yaitu bagaimana merancang antarmuka yang tetap terlihat rapi dan informatif meskipun data dari backend belum sepenuhnya tersedia.

Di sisi CI/CD, pipeline GitHub Actions juga sempat menjadi tantangan. Proses ini gagal karena tes frontend yang terlalu sensitif terhadap perubahan teks pada antarmuka. Karena pertimbangan waktu yang terbatas, saya mengambil keputusan pragmatis untuk menonaktifkan sementara tes yang bermasalah menggunakan `it.skip`. Meskipun bukan solusi ideal, ini menjadi pengingat bagi saya untuk menulis tes yang lebih *robust* di masa depan. Saya juga sempat dibuat pusing oleh error `npm ci` terkait modul `@rollup` yang tidak ditemukan, yang akhirnya bisa saya selesaikan setelah menyadari bahwa ini adalah *bug* npm yang sudah dikenal dan bisa diatasi dengan menambahkan `optionalDependencies`.

## 5. Pembelajaran
Proyek ini benar-benar membuat materi yang saya pelajari pada minggu 9 hingga 15 menjadi lebih nyata. Saya akhirnya memahami bagaimana cara kerja arsitektur microservices dari kacamata frontend, terutama bagaimana frontend harus berkomunikasi dengan berbagai layanan melalui API Gateway. Penerapan *correlation ID* yang saya lakukan di frontend juga terbukti sangat membantu tim untuk melacak alur *request* yang melewati beberapa layanan sekaligus.

Pengalaman *debugging* pada *health check dashboard* tadi juga membuka mata saya tentang betapa pentingnya *observability*. Saya jadi sadar bahwa tanpa *structured logging* dan pengecekan kesehatan yang akurat, mencari sumber masalah akan terasa seperti mencari jarum di tumpukan jerami. Saya juga baru benar-benar merasakan manfaat langsung dari CI/CD di GitHub Actions. Melihat pipeline berwarna hijau memberikan rasa percaya diri saat melakukan *merge*, sementara pipeline berwarna merah memaksa saya untuk berdisiplin memperbaiki kode sebelum merusak lingkungan produksi. Proses *code review* dan penerapan *branch protection rules* juga mengajarkan saya bahwa kode yang berkualitas adalah hasil diskusi tim, bukan kerja yang dilakukan sendiri-sendiri.

## 6. Kesimpulan
Secara keseluruhan, SafeSpace telah mengubah cara pandang saya dalam memandang peran seorang frontend developer. Saya tidak lagi hanya berfokus pada tampilan yang estetis, tetapi juga harus memahami alur data, keamanan, proses *deployment*, hingga cara memantau kesehatan sistem. Jika saya diberi kesempatan untuk mengulang proyek ini, saya akan lebih serius dalam menulis tes otomatis sejak hari pertama agar tidak keteteran di akhir pengembangan. Saya juga akan lebih proaktif dalam menyepakati kontrak API bersama tim backend di fase awal, sehingga proses integrasi bisa berjalan lebih lancar tanpa kejutan di tengah jalan. Pengalaman ini benar-benar menjadi bekal berharga yang akan saya bawa ke tantangan rekayasa perangkat lunak selanjutnya.
